# 对象协作的可靠性
> 用输入校验、异常和测试验证回执与名单，借助回溯和日志定位出错的步骤。

## 7.1 一次失败后，怎样知道名单是否正确

报名服务已经能给出回执。组织者还要知道，收到空学号、重复请求或者满员请求时，原来的名单有没有被改动。如果创建活动时填错容量，程序也要说明问题出在哪里。

| 待核对的情形 | 预期结果 | 预期状态 |
| --- | --- | --- |
| 容量为 1，收到第一个有效学号 | 通过 | 名单恰好有 1 人 |
| 活动已满，同一个学号再次提交 | 重复 | 名单保持原样 |
| 活动已满，收到另一个有效学号 | 满员 | 名单保持原样 |
| 收到空白学号 | 空学号 | 名单保持原样 |
| 创建活动时把容量填为“一个” | 说明容量填写有误 | 活动未创建 |

前四种情形都可以按报名规则交出回执。第五种情形下，创建活动的约定无法完成，调用者需要获得错误原因。下面分别学习怎样表达错误、检查状态和定位偏差。

## 7.2 从症状区分几类失败

程序出现意外时，先确定它运行到了哪里。语法有误时，解释器在开始执行前就可能拒绝代码。运行时异常则说明执行到某一步时无法继续。还有一种情况，程序正常运行，却产生了不合规则的结果。

| 现象 | 独立例子 | 如何定位 |
| --- | --- | --- |
| 语法有误 | 分支标题漏了冒号 | 阅读 `SyntaxError` 指示的位置，并检查前后代码 |
| 执行时无法完成操作 | 用 `int("三个")` 转换文字 | 查看异常类型、消息和调用回溯 |
| 结果不合规则 | 计价时把每件费用加到件数上 | 比较预期与实际，再追踪中间值 |
| 业务请求被拒绝 | 库存为零，无法领用 | 把“无库存”作为约定好的返回结果 |

业务规则可以允许请求被拒绝。拒绝结果仍能交给调用者继续处理，例如显示原因。输入连所需的类型或取值条件都不满足时，函数可以报告异常，交给知道如何应对的一方处理。

## 7.3 在边界校验并处理异常

### 从数据到可用的对象

来自表单、文件或其他系统的数据，需要先检查能否转换为所需类型，再核对允许的取值。比如把页数文本转换成整数，再检查它是否大于零。转换完成与符合业务规则是两项独立的检查。函数或方法应在改动状态前完成它负责的检查。

可以把校验分为几个问题。输入的形状和类型是否正确，能否转换为程序使用的值，取值是否符合范围，字段之间的关系是否一致。例如读到“24”时可以转换为整数，读到“0”时也能转换，但页数还需要大于零。

| 边界检查 | 可能发现的问题 | 谁适合做这项检查 |
| --- | --- | --- |
| 类型或形状 | 文本位置收到列表 | 接收请求的入口 |
| 转换 | “二十四”无法用 `int()` 按数字转换 | 解析输入的函数 |
| 取值 | 页数小于等于零 | 使用页数的对象或规则函数 |
| 状态关系 | 起始页超过总页数 | 维护页数和范围的对象 |

能在修改前完成的检查尽量提前。这样调用者可以用同一份原状态调整输入再试，也能通过测试核对失败发生在哪里。

### 用 try、except、else 和 finally 表达处理过程

当函数无法按约定交出结果时，可以用 `raise` 抛出异常。异常会沿调用链向外传播，直到遇到能处理它的 `except`。适合处理异常的位置通常知道下一步该怎么做，例如提示用户重新填写。

| 部分 | 负责的工作 |
| --- | --- |
| `try` | 放入可能发生预期异常的操作 |
| `except ValueError as error` | 处理指定类型的异常，并取得异常对象 |
| `else` | `try` 正常执行完毕后，继续使用结果 |
| `finally` | 在离开整个结构前执行收尾动作 |

```python
def parse_pages(text):
    try:
        pages = int(text)
    except ValueError as error:
        raise ValueError("页数应填写整数") from error
    if pages <= 0:
        raise ValueError("页数须大于零")
    return pages


for raw in [" 24 ", "二十四", "0"]:
    try:
        pages = parse_pages(raw)
    except ValueError as error:
        print("请修改输入", error)
    else:
        print("准备生成页码", pages)
    finally:
        print("本次检查结束")
```

转换失败时，`raise ... from error` 在提供更清楚的提示时保留原异常作为原因。把 `try` 限定为预期可能失败的操作，能明确哪一步的错误由这个 `except` 负责。超出它能处理的情况会继续向外传播。[Python 官方教程的异常处理](https://docs.python.org/3.12/tutorial/errors.html)

### 在边界保留异常的含义

`except` 可以选择一种异常，也可以用元组处理几种需要同样应对的异常。要对一类更具体的异常单独处理时，应把它写在能捕获它的基类之前。比如，读取文件时可以先处理 `FileNotFoundError`，再考虑范围更广的 `OSError`。

领域中有需要专门处理的失败，也可以定义自己的异常类。下面的查找函数把字典的缺键转换成更容易理解的“缺少读数”，同时保留底层原因。

```python
class MissingReading(LookupError):
    pass


def require_reading(readings, station):
    try:
        return readings[station]
    except KeyError as error:
        raise MissingReading(f"还没有 {station} 的读数") from error


try:
    value = require_reading({"东站": 0}, "西站")
except MissingReading as error:
    print("给调用者的说明", error)
    print("底层异常的类型", type(error.__cause__).__name__)
else:
    print("可用于计算的读数", value)
```

上层能根据 `MissingReading` 决定是否提示补录，调试时仍可通过原因找到缺少的键。只记录一下错误后需要让它继续传播时，可以在 `except` 内写空的 `raise`。`finally` 适合做退出时必须完成的收尾，后续也可以用 `with` 管理常见资源。

## 7.4 让状态在成功和失败后都可解释

### 先检查，再更新

状态约束应该在构造和更新后都成立。下面的计量对象只接收一定范围内的整数。尝试无效更新时先报告问题，随后读取对象，可以得到失败前的合法状态。

```python
class Gauge:
    def __init__(self, value):
        self.update(value)

    def update(self, value):
        if type(value) is not int or not 0 <= value <= 100:
            raise ValueError("读数须为 0 到 100 的整数")
        self.value = value


gauge = Gauge(40)
try:
    gauge.update(130)
except ValueError as error:
    print("更新失败", error)
print("当前读数", gauge.value)
```

如果把赋值放到检查之前，报告失败时对象可能已经保存了非法值。测试要同时核对报告的异常和调用后的状态。

### 一个流程可以完成一部分工作

协作可能包含几项分别完成的操作。例如，先记录一笔领用，再发送提醒。如果第二步失败，第一步的记录仍然存在。调用者需要分别知道领用和提醒各自的结果，才能决定下一步是重新领用还是补发提醒。第 10 章会用测试验证这种情况。

| 进展 | 可交出的结果 | 下一步能做什么 |
| --- | --- | --- |
| 领用记录未保存 | 说明保存失败 | 排查保存问题，之后再提交 |
| 记录已保存，提醒失败 | 领用完成，提醒待发 | 读取已有记录，单独补发提醒 |
| 两项工作都完成 | 领用完成，提醒已发 | 查阅记录和发送结果 |

画出状态在哪一步发生变化，再安排异常处理。这样可以准确说明失败影响的是哪一步，也能据此选择是否需要重试。

## 7.5 用断言和测试检查程序

不变式是每次有效操作前后都应成立的关系。一个只允许 0 到 100 的百分比值，在构造与更新后都应满足范围约束。`assert` 可检查开发时预期成立的内部条件。解释器以优化模式执行时可以省略 `assert`，所以外部输入的校验应写成显式的 `if` 和 `raise`。

用例从可重复的初始状态出发，提供输入，再比较实际结果和预期结果。状态可能发生变化时，还要检查对象是否按契约更新。选择用例时可以先列出正常情况，再查看边界值、非法输入和操作失败后的状态。

```python
import unittest


def percent(part, total):
    if total <= 0 or not 0 <= part <= total:
        raise ValueError("比例须满足 0 ≤ 部分 ≤ 总量，且总量大于零")
    return part * 100 / total


class PercentTests(unittest.TestCase):
    def test_bounds(self):
        self.assertEqual(percent(0, 5), 0)
        self.assertEqual(percent(5, 5), 100)

    def test_invalid_total(self):
        with self.assertRaises(ValueError):
            percent(0, 0)


suite = unittest.defaultTestLoader.loadTestsFromTestCase(PercentTests)
unittest.TextTestRunner().run(suite)
```

`TestCase` 是标准库提供的测试基类。括号里的类名表示继承，测试类可以使用基类的断言方法。示例的加载器收集以 `test_` 开头的方法，再交给运行器执行。`assertEqual` 负责比较结果，`assertRaises` 检查指定代码块是否产生约定的异常。[Python 官方文档的 unittest](https://docs.python.org/3.12/library/unittest.html)

### 让每个用例得到自己的初始状态

测试可以把准备、执行和核对写成三个明确步骤。测试类中的 `setUp()` 在每个测试方法前执行，适合准备一份新对象。若同一个方法有几组相似输入，可以用 `subTest()` 标出当前输入，报告中会包含发生偏差的那一组。

```python
import unittest


def reserve(available, requested):
    if requested <= 0:
        raise ValueError("申请量须为正数")
    if requested > available:
        return available, "不足"
    return available - requested, "已预留"


class ReserveTests(unittest.TestCase):
    def setUp(self):
        self.available = 2

    def test_allowed_requests(self):
        for requested, expected in [(1, (1, "已预留")), (2, (0, "已预留"))]:
            with self.subTest(requested=requested):
                self.assertEqual(reserve(self.available, requested), expected)

    def test_too_many(self):
        self.assertEqual(reserve(self.available, 3), (2, "不足"))

    def test_invalid_request(self):
        with self.assertRaisesRegex(ValueError, "正数"):
            reserve(self.available, 0)


suite = unittest.defaultTestLoader.loadTestsFromTestCase(ReserveTests)
unittest.TextTestRunner(verbosity=2).run(suite)
```

恰好用完、差一个就不够、请求量为零，分别检验三个决策边界。`assertRaisesRegex()` 同时核对异常类型和消息中的线索。状态变化的用例可以比较完整数据，而不仅比较数量，避免遗漏“人数相同但名单不同”这类偏差。

### 区分内部断言和调用者能依赖的行为

| 工具 | 用途 | 举例 |
| --- | --- | --- |
| 普通条件与 `raise` | 运行中的输入检查 | 收到负数时报告非法容量 |
| `assert` | 开发时检验内部假设 | 累计值和记录条数符合约定 |
| `assertEqual()` | 在测试中核对值 | 名单与预期元组相等 |
| `assertIs()`、`assertIsNone()` | 在测试中核对对象或缺失值 | 查找无结果时交出 `None` |
| `assertRaises()` | 在测试中核对失败方式 | 非法调用产生预期异常 |

修复一次问题时，可以先写一个能暴露它的测试，再调整程序。这个用例随后可以保留下来，每次修改后重复运行，检查曾经修好的行为是否再次出错。

## 7.6 用回溯、调试与日志定位

先用尽可能小的输入重现问题。如果发生异常，从回溯末尾读取异常类型和消息，再查看属于自己程序的调用位置。如果测试只报告结果有偏差，可在关键分支前打印一次中间值，或用调试器暂停并检查当前对象和局部变量。确认原因后，用同一个测试验证修复。

### 沿调用链找最早可解释的偏差

例如，汇总函数调用读数转换，转换时收到“待测”。可以先读回溯末尾的异常信息，再向上追踪哪一层传入了这段文字。下面把回溯中的函数名提取出来，在网页里观察调用顺序。

```python
from traceback import extract_tb


def parse_reading(text):
    return int(text)


def describe_reading(text):
    reading = parse_reading(text)
    return f"读数 {reading}"


try:
    print(describe_reading("待测"))
except ValueError as error:
    print("异常类型", type(error).__name__)
    print("错误说明", error)
    print("回溯中的调用", [frame.name for frame in extract_tb(error.__traceback__)])
```

最后一个位置对应抛出异常的调用，前面是它经过的层次。调试时可以在 `parse_reading` 的入口观察收到的值，再回到 `describe_reading` 看它从哪里取得这个值。遇到逻辑错误时，也可以按照“最小输入、预期、实际、产生偏差的第一步”的顺序检查。

### 用日志保留有用的运行信息

日志用来记录运行中的事件。应用入口可以设置格式和记录级别，各模块用 `logging.getLogger(__name__)` 取得日志器。`DEBUG` 用于诊断细节，`INFO` 记录正常进度，`WARNING` 提醒值得注意的情况，`ERROR` 记录无法完成的操作。

```python
import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
logger = logging.getLogger(__name__)
valid = 2
skipped = 1

logger.debug("开始汇总采样")
logger.info("已汇总 %s 条有效记录", valid)
if skipped:
    logger.warning("跳过 %s 条缺失记录", skipped)
```

当前级别下会显示 `INFO` 和 `WARNING`。把级别改为 `logging.DEBUG` 再运行，观察多出的诊断记录。设计日志时，记录能定位问题的操作、结果和数量即可。[Python 官方日志指南](https://docs.python.org/3.12/howto/logging.html)

输出给使用者的回执用于完成任务，诊断日志面向排查程序状态。可以在日志中记录操作、结果和数量。异常处理处需要记录回溯时，`logger.exception()` 可以附上正在处理的异常。日志可以帮助找到要重现的问题，修复后仍可用测试核对实际行为。

## 7.7 回到案例 为报名规则编写测试

把“容量文本能否转换为整数”留给创建活动的入口，把“容量是否非负”留给活动初始化。报名方法在收到有效文本后依次检查空白、重复和满员。每个测试使用独立的活动，验证回执以及报名方法对状态的影响。

### 先写出一个能发现偏差的用例

下面的登记函数故意把满员检查放在前面。先保留这处问题，在 `verify_duplicate_when_full()` 里写两条检查。容量为 1、名单已含 S01 时，再提交 S01 应回执「重复」，名单仍应与提交前相同。先运行，看到回执检查失败后再调整判断顺序，重跑两条检查。

```python registration-regression
def register(student_id, roster, capacity):
    if len(roster) >= capacity:
        return "满员"
    if student_id in roster:
        return "重复"
    roster[student_id] = "已报名"
    return "通过"


def verify_duplicate_when_full():
    roster = {"S01": "已报名"}
    before = roster.copy()
    receipt = register("S01", roster, capacity=1)
    # 在这里分别断言回执和名单。
    raise NotImplementedError("请先写出两条检查")


verify_duplicate_when_full()
print("回执和名单检查通过")
```

:::answer
可用 `assert receipt == "重复", f"实际回执为 {receipt}"` 和 `assert roster == before, "名单发生变化"` 替换占位语句。第一次运行时，实际回执为“满员”。让重复判断先执行后，两条检查都会通过。
:::

### 用多组请求检验完整活动对象

| 输入或情形 | 由谁检查 | 预期反馈 |
| --- | --- | --- |
| 容量是“一个”或负数 | 转换入口和活动初始化 | `ValueError` |
| 容量输入不是文本 | 转换入口 | `TypeError` |
| 学号不是字符串 | 登记方法 | `TypeError`，名单保持原样 |
| 学号为空白、重复或已满 | 登记方法 | 对应的业务回执，名单保持原样 |
| 两个活动收到同一学号 | 各活动维护自己的名单 | 两边可分别通过 |

```python
import unittest


class Activity:
    def __init__(self, capacity):
        if type(capacity) is not int:
            raise TypeError("容量须为整数")
        if capacity < 0:
            raise ValueError("容量须为非负整数")
        self._capacity = capacity
        self._roster = {}

    def student_ids(self):
        return tuple(self._roster)

    def register(self, raw_id):
        if not isinstance(raw_id, str):
            raise TypeError("学号须为字符串")
        student_id = raw_id.strip()
        if not student_id:
            return "空学号"
        if student_id in self._roster:
            return "重复"
        if len(self._roster) >= self._capacity:
            return "满员"
        self._roster[student_id] = "已报名"
        return "通过"


def create_activity(raw_capacity):
    if not isinstance(raw_capacity, str):
        raise TypeError("容量输入须为文本")
    try:
        capacity = int(raw_capacity)
    except ValueError as error:
        raise ValueError("容量应填写整数") from error
    return Activity(capacity)


class RegistrationTests(unittest.TestCase):
    def test_fills_last_place(self):
        activity = create_activity(" 1 ")
        self.assertEqual(activity.register(" S01 "), "通过")
        self.assertEqual(activity.student_ids(), ("S01",))

    def test_rejections_leave_full_roster_unchanged(self):
        activity = Activity(1)
        activity.register("S01")
        before = activity.student_ids()
        for raw, expected in [("S01", "重复"), ("S02", "满员"), (" ", "空学号")]:
            with self.subTest(raw=raw):
                self.assertEqual(activity.register(raw), expected)
                self.assertEqual(activity.student_ids(), before)

    def test_zero_capacity(self):
        activity = Activity(0)
        self.assertEqual(activity.register("S01"), "满员")
        self.assertEqual(activity.student_ids(), ())

    def test_activities_are_independent(self):
        first = Activity(1)
        second = Activity(1)
        self.assertEqual(first.register("S01"), "通过")
        self.assertEqual(second.student_ids(), ())
        self.assertEqual(second.register("S01"), "通过")
        self.assertEqual(first.student_ids(), ("S01",))

    def test_invalid_input(self):
        with self.assertRaises(ValueError):
            create_activity("一个")
        with self.assertRaises(ValueError):
            create_activity("-1")
        with self.assertRaises(TypeError):
            create_activity(1.5)
        activity = Activity(1)
        with self.assertRaises(TypeError):
            activity.register(101)
        self.assertEqual(activity.student_ids(), ())


suite = unittest.defaultTestLoader.loadTestsFromTestCase(RegistrationTests)
unittest.TextTestRunner(verbosity=2).run(suite)
```

运行结果应显示 5 个测试通过。`subTest` 标出满员后分别收到的三个输入。读取报告时可以把用例名、输入和失败的断言连起来看。例如次序写错时，`test_rejections_leave_full_roster_unchanged` 会说明哪条请求的回执不对。

把名单转成元组后再保存在 `before` 中，核对的是操作前的状态。如果只是把同一份可变字典绑定给两个名字，之后原地修改时两处都会看到变化，可能掩盖错误。这里用第 2 章的快照办法，让预期值独立于待检验的操作。报名数据要从文件恢复时，同样需要检查读取结果和失败后保留的状态。[第 8 章 对象与外部环境的协作](08.md)

下一章会把“失败后仍能读到原内容”的预期写成检查，验证保存文件的步骤。[进入文件保存练习](08.md#file-regression)

- 在无效容量测试中增加 `create_activity("0")` 的检查。判断构造是否成功，再检查它收到新学号时的回执。
