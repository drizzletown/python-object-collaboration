# 综合项目 递归假设驱动的程序构造
> 从报名请求到文件保存，用可替换的存储验证主流程，再逐层兑现存储和数据校验。

## 9.1 确定交付范围与验收条件
交付一个命令行报名程序。首次运行建立博物馆活动，容量为 2。输入学号可以报名，另一个命令可列出已保存名单。清理首尾空白，拒绝空学号，优先判断重复，再判断满员。退出后再次运行能读取上一次成功保存的数据。已有文件损坏时报告错误并保留原文件。
用五个场景验收：第一次报名成功；同一学号再次提交得到重复；第二个学号成功且名额耗尽；第三个学号得到满员；重新创建存储对象后仍能读取两条记录。再用一份超容量 JSON 检查读取失败时文件未被覆盖。这个版本适用于同一时刻由一个命令进程操作一份名单的教学场景。

## 9.2 建立并使用存储假设
先约定存储对象可以 load 读出独立的活动快照，并通过 save 保存成功后的活动。主流程依赖这两个操作，先读再判断，只有成功报名才保存，且保存成功后才产生通过回执。这个顺序防止用户看到尚未写入文件的成功消息。
现在还没有文件实现，可以让 MemoryStore 在内存里保存活动并复制快照。它兑现了测试所需的行为，足够验证主流程。下面的程序展示领域对象、内存存储、文件存储和命令行入口如何组合。先看 submit，再运行演示，观察两种存储产生相同回执。

## 9.3 逐层兑现文件存储
兑现文件存储假设时产生两个子问题。读取需要把 JSON 转为可靠的活动对象，保存需要在写入成功后替换旧文件。先约定 activity_from_data 接收字典并返回符合约束的 Activity，用这个假设写出 JsonStore.load。再分别核对容量类型、编号规范、重复以及超容量，把契约落到实现。
保存使用同目录的临时文件。完整写入并关闭后替换正式文件，清理可能留下的临时文件。这样，序列化出错时旧文件仍可读取。最后让集成检查使用一个临时目录，实际经历保存、重新打开和读取损坏数据的路径。子任务完成后，回到最初的五个场景验收主流程。

:::project

下载上方 Python 文件后，在终端进入文件所在目录。运行 python campus.py 自带演示，运行 python campus.py --self-test 执行验收。运行 python campus.py enroll S01 登记，再运行 python campus.py list 查看名单。可在子命令前加 --file demo.json 指定数据文件。请使用虚构学号。
网页版运行完整代码时会启动演示。每次点击运行都重新初始化练习文件环境，持久化效果体现在一次运行中的多次读取。本机的 enroll 与 list 可以跨进程读取同一文件。

## 9.4 用需求追踪一次修改
若组织者希望“满员时也记录候补”，先约定候补名单的顺序、唯一性和取消规则，再判断哪些角色需要变化。领域对象维护正式与候补的关系，存储层处理新增字段，主流程根据新增回执决定是否保存。先把旧 JSON 当作一个单独的输入场景，确定它如何补全候补字段。
本章的设计沿“先有能调用的契约、再有可验证的实现”前进。依赖方向由主流程通向存储约定，测试可以在实现顺序变化时继续检查相同的报名行为。
