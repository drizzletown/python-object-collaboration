# 综合项目 递归假设驱动的程序构造
> 用假设三部曲构造校园活动报名系统，先验证主流程，再兑现文件存储与数据校验。

## 9.1 把报名程序交付给活动组织者

组织者需要在开放报名时受理学号，关闭程序后还可以打开同一份名单。第一个版本管理一场容量为 2 的博物馆参观活动，由一个运行中的程序操作这份名单。入口需要支持提交学号和查看当前名单。

| 验收场景 | 预期结果 |
| --- | --- |
| 依次提交 ` S01 `、空白、`S02`、`S03`、`S01` | 回执依次为“通过、空学号、通过、满员、重复” |
| 处理完请求后重新打开名单 | 按报名顺序读出 `S01` 和 `S02` |
| 首次使用时只提交空白 | 给出“空学号”回执，尚未创建名单文件 |
| 打开损坏、重复或超容量的旧名单 | 报告数据错误，保留文件原来的内容 |
| 取到快照后只在内存中试算 | 已保存的名单仍是试算前的状态 |

要把前面几章的能力接起来，需要先确定主流程应从其他组件取得哪些结果。这样即使负责文件存储的组件还没实现，也可以先把主流程写出来并检验规则。

### 从验收结果反推要完成的工作

“能报名”包含了检查学号、更新名单、保存结果和报告回执。“下次打开能继续”则要求程序能把文件中的数据恢复成满足规则的活动对象。先分别写出这些结果如何验收，才容易判断一个步骤失败时应该由哪一层处理。

可以先用同一份空名单设计五条请求。前三条检查清理学号、拒绝空白和按顺序登记，名单应依次加入 S01 和 S02。后两条用已经满员的状态检查优先级。需要重读的场景，则要使用新创建的存储对象读取原来的路径。这样才真正经过文件边界。

## 9.2 把假设写成可以调用的契约

假设三部曲中的“建立”要给出一项能力的输入和输出。“使用”要拿到假设承诺的结果，并说明结果推动了哪一步。“兑现”时可以自己实现、由合作者实现，或用现成的库完成。若某个实现又遇到难题，就把它当作子任务，在这个层次再次建立、使用和兑现假设。

以一份气温摘要为例。先假设有一个读取函数能返回一组可用于计算的温度。摘要函数拿到数据，检查是否为空，再计算并呈现平均温度。早期用一组固定数据兑现读取约定，便可检验摘要。将来可交给另一个函数读取实际数据，并在读取函数中处理文件和校验。

```python
def summarize(read_temperatures):
    values = read_temperatures()
    if not values:
        return "没有可用读数"
    average = sum(values) / len(values)
    return f"平均温度 {average:.1f} ℃"


def sample_readings():
    return [18, 21, 24]


print(summarize(sample_readings))
print(summarize(list))
```

第一次调用取得三条读数，继续计算得到 `21.0 ℃`。第二次调用把内置的 `list` 作为读取能力，无参数调用时得到空列表，由此可以检查没有数据时的处理。以后换用读取实际文件的函数，只要结果符合这个契约，摘要步骤就可以继续使用。

### 用交付物写假设

| 写出什么 | 气温摘要中的约定 | 可以怎样检查 |
| --- | --- | --- |
| 需要的输入 | 读取函数已经知道数据来源 | 用固定输入运行摘要 |
| 返回的对象 | 一组数值，缺少数据时交出空列表 | 分别提供三条读数和空列表 |
| 结果的用途 | 判断能否计算平均值，再决定显示内容 | 核对两种输出 |
| 失败应传到哪里 | 读取失败交由调用摘要的一方处理 | 用会抛异常的读取函数复现 |

把假设写成“系统可以读取数据”时，还无法据此计算或测试。说明会交出数值列表，下一步就能使用 `len()` 和 `sum()`。等到交接工作明确后，可以并行考虑真实的数据来源、错误报告与校验方式。

## 9.3 选择假设的实现，并在层次之间验证

### 函数、对象和协议怎样承担契约

| 需要承诺的能力 | Python 中的表达 | 可以怎样验证 |
| --- | --- | --- |
| 取得一个结果 | 约定函数参数、返回值及失败行为 | 用固定输入检查结果 |
| 维护一组相关状态 | 用对象和方法承诺更新规则 | 调用前后比较对象状态 |
| 换用多个具备相同操作的实现 | 用文档约定行为，可用 `Protocol` 标注方法的形状 | 用同一组场景检查不同实现 |
| 调用文件、编码等外部能力 | 通过独立函数或对象使用标准库 | 用临时文件或目录验证读写 |

协议可以声明调用者需要的方法、参数类型和返回类型。像“读出的快照是否独立”这样的行为，需要在文档中明确，再通过测试核对。第 10 章会进一步解释协议怎样支持替换。

### 先验证主流程，再验证外部边界

负责业务规则的对象只关心允许哪些更新。负责存储的对象把持久化细节留在自己的方法里。主流程按约定取得快照、执行规则，再决定是否提交保存。快照让一次试算或尚未保存的修改与已保存状态分开。

逐层验证可以从小到大推进。先用内存实现验证判断、更新和回执。再用真实的临时文件验证编码、校验和重新读取。最后通过入口观察一条请求怎样到达存储，以及出错时用户会看到什么。

### 区分规则、协调和资源

规则负责判定一项操作是否允许，例如数量是否能再增加。协调负责把几项能力串起来，例如先读、再算、最后决定是否保存。资源实现负责怎样取得原数据或写入新数据。可以沿主流程画出依赖方向。

```text
入口取得一条请求
    主流程请存储交出当前状态
    主流程请业务对象处理请求
    主流程根据结果决定是否要求保存
入口取得回执并呈现
```

先通过契约连接这些层次。规则的输入可以来自内存，也可以来自已解析的文件。处理后要保存时，主流程可以通过同一种约定调用不同实现。这样能在更换外部资源时保留原有规则。

## 9.4 先让成功与失败路径可检验

### 用一个小实现观察读、改、存的次序

以追加一条读数为例。假设读取能力会交出一份独立列表，保存能力能接收更新后的列表。主流程用读到的列表追加读数，保存后再返回新的条数。调用者可以提供一个故意失败的保存函数，观察是否留下了任何更新。

```python
def record_reading(load, save, value):
    readings = load()
    readings.append(value)
    save(readings)
    return len(readings)


current = [18]

def load_snapshot():
    return current.copy()


def save_to_memory(readings):
    current[:] = readings


def reject_save(readings):
    raise OSError("存储暂不可写")


try:
    print("已记录的条数", record_reading(load_snapshot, reject_save, 21))
except OSError as error:
    print("保存失败", error)
print("保存失败后的记录", current)
print("保存成功后的条数", record_reading(load_snapshot, save_to_memory, 21))
print("现在的记录", current)
```

两次调用使用相同的更新逻辑。第一次在副本上追加后保存失败，调用处获得错误，原记录只有 18。第二次保存成功，调用处得到两条记录。若把读取函数改成直接交出 `current`，第一次追加就会修改原记录。这个试验验证了“独立快照”这个行为约定。

### 让每层的测试回答不同问题

| 验证层次 | 应回答的问题 | 常用办法 |
| --- | --- | --- |
| 业务规则 | 输入在边界时得到什么结果 | 直接构造对象，核对状态 |
| 主流程 | 何时读，何时保存，何时交回结果 | 传入可控的实现，记录实际行为 |
| 资源实现 | 内容怎样保存，能否重新取得 | 用真实临时文件做往返测试 |
| 入口 | 用户看见的结果是否清楚 | 运行完整示例，核对输出 |

开发时可以先完成其中最容易验证的一层。真实存储还在编写时，主流程依然能靠内存实现推进。等到文件存储兑现后，用同样的输入复查规则，再增加只有外部资源才会发生的测试。

## 9.5 回到案例 先兑现报名主流程

校园报名项目先约定一个存储对象能读取并保存活动。主流程先使用这一能力取到活动快照，再请活动判断登记，接着使用回执决定是否保存。

```text
任务：受理报名并交出回执
    1. 输入
        1.1 一条学号请求和当前活动的存储对象。
    2. 处理：建立假设
        2.1 存储对象能交出独立的活动快照，并能保存更新后的活动。
    3. 处理：使用假设
        3.1 从存储取到活动快照，用快照处理请求，取得报名回执。
        3.2 回执为“通过”时，先把更新后的活动交给存储。
            3.2.1 保存完成后，交出“通过”回执。
        3.3 回执为其他结果时，直接交出回执。
    4. 处理：兑现假设
        4.1 先用内存存储核对报名规则和名单。
        4.2 再用 JSON 文件存储，核对重新打开后的名单。
    5. 输出
        5.1 报名回执。若读取或保存失败，交由入口报告原因。
```

`Activity.register` 处理规则并维护单场活动的名单。`Store` 约定 `load()` 返回独立的活动快照，`save(activity)` 保存成功后的状态。`MemoryStore` 用深复制保存和交出活动。即使调用者改变取出的快照，已保存的内存状态仍保持原样，直到调用 `save`。

### 约定两个存储操作

| 操作 | 给主流程的保证 | 对状态的影响 |
| --- | --- | --- |
| `load()` | 取得可修改的独立活动快照 | 读取当前保存状态 |
| `save(activity)` | 正常返回表示已保存，失败时抛出异常 | 更新保存状态 |
| `submit(store, raw_id)` | 返回规则给出的回执，通过时已完成保存 | 只在登记通过时请求写入 |

如果只有空白、重复或满员回执，主流程直接交回业务结果。第一次收到空白时，存储虽然能交出一份初始活动，主流程仍无需创建文件。快照是否独立可先在内存版本验证，例如读取活动并在副本中登记一人，再次读取时应得到此前保存的名单。

## 9.6 在子任务中兑现文件存储

兑现文件存储时，读取和保存各自形成一个子任务。读取需要一个能从文件数据交出有效活动的能力，保存需要一个能用完整新文件替换正式文件的过程。主流程继续沿用相同的 `load` 和 `save`。

### 子任务一 从文件交出可用的活动

先约定 `activity_from_data` 接收解析后的数据并返回有效的 `Activity`。有了这个约定，`JsonStore.load` 就可以先读文本、解析 JSON，再把返回的活动交给报名主流程。兑现时，检查 `title`、`capacity`、`students`，并按活动规则逐个恢复学号。只在确实没有名单文件时构造初始活动。解析或校验失败时，错误传到调用者。

可以把读取再分成三项动作。取得文本时，区分确实没有文件和其他访问错误。解析文本时，将 JSON 转成基础对象。恢复活动时，让字段满足活动的约定，最后才交出可用于登记的实例。写出这几个层次之后，主流程仍然只需要知道 `load()` 会交回什么。

| 要校验的内容 | 恢复时的处理 |
| --- | --- |
| 标题和容量 | 由 `Activity` 初始化检查，容量须为非负整数 |
| 学号字段的形状 | `students` 应是列表，各项应为已整理的字符串 |
| 空学号、重复、超容量 | 逐条交给 `register()`，必须每条都通过 |
| 原有顺序 | 按数组顺序调用登记，快照也按这个次序交付 |

`activity_from_data()` 创建的是一份新的活动。遇到某一项失败时，可以丢弃这份尚未交给上层的对象。重新使用合法数据时，已有文件仍能被读取。

### 子任务二 完成保存后再交回执

先把活动状态转成三个字段组成的字典。用标准库在目标目录中创建临时文件，把完整 JSON 写入并关闭，再通过 `Path.replace` 替换正式文件。若序列化失败，程序还没开始替换，旧文件仍可读取。主流程在 `save` 正常返回后才交出“通过”。

### 先确认哪些状态需要保存

保存的数据只包含标题、容量和学号列表。剩余名额可以从容量和名单算出，读取时根据恢复后的实际记录计算即可。`save()` 完成后，另一个 `JsonStore` 指向同一路径，就能读取刚保存的数据。

保存动作本身若失败，错误从 `save()` 经过 `submit()` 到入口。这样用户得到的是保存失败的原因。若输入属于满员或重复，流程连写入临时文件这一步都不会进入。两个结果有清楚的发生位置。

## 9.7 运行项目并对照验收条件

### 独立交付余量查询

为报名系统实现 `remaining(store)`。它应交回一个整数，供显示或其他步骤使用。先根据下表写出函数，再运行验收。遇到困难时，可以先假设 `load()` 会交回一个活动，用这个对象设计查询。

| 情形 | 预期余量 | 同时检查 |
| --- | --- | --- |
| 第一次查询，尚无名单文件 | 2 | 查询后仍无文件 |
| 登记 S01 后查询 | 1 | 保存的名单仍只有 S01，文件内容与查询前相同 |
| 再次提交 S01 后查询 | 1 | 回执为「重复」，名单和文件内容保持原样 |

```python remaining-task campus
from pathlib import Path
from tempfile import TemporaryDirectory
from campus import JsonStore, submit


def remaining(store):
    # 返回当前活动的剩余名额。
    raise NotImplementedError("请先实现 remaining()")


with TemporaryDirectory() as folder:
    path = Path(folder) / "roster.json"
    store = JsonStore(path)
    first = remaining(store)
    assert first == 2, "首次查询应有两个名额"
    assert not path.exists(), "首次查询不应创建文件"

    assert submit(store, "S01") == "通过"
    before = path.read_text(encoding="utf-8")
    after = remaining(store)
    assert after == 1, "登记后应剩一个名额"
    assert path.read_text(encoding="utf-8") == before, "查询改变了文件内容"

    assert submit(store, "S01") == "重复"
    repeated = remaining(store)
    assert repeated == 1, "重复提交后余量应相同"
    assert store.load().students == ("S01",), "名单应只有 S01"
    assert path.read_text(encoding="utf-8") == before, "原文件内容发生变化"
    print("初始、登记后、重复后的余量", first, after, repeated)
    print("余量查询验收通过")
```

:::answer
用 `activity = store.load()` 取得快照。容量在 `activity.capacity`，已报名学号在 `activity.students`。查询只需要读取这些数据。

```python remaining-reference campus solution
from campus import Activity, MemoryStore, submit


def remaining(store):
    activity = store.load()
    return activity.capacity - len(activity.students)


store = MemoryStore(Activity("博物馆参观", 2))
print("初始余量", remaining(store))
print("报名回执", submit(store, "S01"))

```

入口 `main` 负责组织 `enroll` 和 `list` 两个操作。它把存储异常转换成清楚的错误消息，规则与读写各自由对应的对象完成。做完查询功能后，可以继续给回执增加一种通知方式。[进入第 10 章的通知练习](10.md#notifier-task)

### 从输出判断是哪一层出了偏差

如果内存版和文件版都在第 5 步回执“满员”，先检查活动规则中的判断顺序。如果内存结果正常，重读文件后名单顺序发生变化，重点检查数据转换和存储。如果读到坏数据却生成了空名单，检查 `load()` 是否把格式错误也当成了首次运行。

只看“项目验收通过”还可以追问它覆盖了什么。自测包含快照独立、首次空请求、五条回执、重读和坏文件保持原样。若将来增加取消或候补，需要为新操作定义回执、保存条件与旧文件恢复方式，再把新场景加入自测。[第 10 章 对象协作系统的复用与演化](10.md)
