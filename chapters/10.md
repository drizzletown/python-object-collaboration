# 对象协作系统的复用与演化
> 给校园报名系统接入可替换的通知方式，用测试核对回执、名单和通知结果。

## 10.1 报名已经完成，回执可以发到哪里

第 9 章的项目会把报名结果交给调用者。现在活动组织者需要在终端查看回执，测试程序需要把同一批回执收集起来，逐条核对。以后若接入外部通知服务，还要能辨认报名已保存、通知却未完成的情形。

- 两种通知方式都应收到相同的回执内容，报名请求仍由第 9 章的程序处理。
- 通过报名时先保存再通知。空学号、满员和重复都应有自己的回执。
- 已保存的报名遇到通知故障时，应同时报告报名“通过”和“通知待处理”。用同一组用例验证更换通知方式前后的名单。

要做到这些，程序需要明确哪些能力可以替换、各自遵守什么约定。下面先用小例子比较 Python 中组织和复用行为的几种方式。

可先把变化分成两部分。通知目的地会变，回执内容和报名状态必须有可比较的预期。存储失败发生在回执返回前，通知失败发生在取得回执后。用两组用例分别检查，才能知道哪一步已经完成。

## 10.2 用组合和协议约定可替换能力

### 通过组合选择要使用的对象

当一项工作的一部分有多种实现，可以把这个能力交给单独的对象。下面的报告函数只需要一个能够接收字符串的输出端。输出端可以显示文字，也可以保存文字供后续使用。

```python
from typing import Protocol


class TextSink(Protocol):
    def write(self, text: str) -> None:
        ...


class Screen:
    def write(self, text: str) -> None:
        print(text)


class Buffer:
    def __init__(self):
        self.lines = []

    def write(self, text: str) -> None:
        self.lines.append(text)


def report(value: float, target: TextSink) -> None:
    target.write(f"测量结果 {value:.1f}")


report(18.0, Screen())
buffer = Buffer()
report(18.0, buffer)
print(buffer.lines)
```

同一个调用位置可以通过共同约定使用不同对象，这体现了多态。`Protocol` 把调用者需要的能力写成类型标注。两个类只要提供兼容的 `write` 方法，就能满足静态类型检查所要求的形状。方法的实际行为仍要用测试检查，例如每次调用应该写入一条完整的记录。[Python 官方文档的 Protocol](https://docs.python.org/3.12/library/typing.html#typing.Protocol)

### 协议说明调用形状，契约说明使用结果

`TextSink` 描述 `write(text: str) -> None`。实现类可以各自定义这项能力，无需继承某个输出类。调用时 Python 会调用对象实际提供的 `write()`。类型检查工具可以提前发现名称、参数或返回类型不合约定的实现。

| 约定层次 | 要核对的问题 |
| --- | --- |
| 方法形状 | 能否用一个字符串调用，调用者是否需要使用返回值 |
| 行为 | 一次调用是否处理一条完整文字，是否按顺序接收 |
| 失败 | 失败怎样告诉调用方，之前已完成的工作能否读取 |

协议标注主要说明方法形状。能接收文字的对象如果把每行都悄悄丢掉，仍可能符合方法形状。把同一组输入交给不同实现，检查接收的内容和次数，才能验证实际行为。

### 组合已有能力形成新的行为

假设数据显示时需要加一个前缀，核心数据仍应交给原有的输出端。可以用一个对象保存下游的输出能力，在转发前处理文字。调用者仍按相同的 `write()` 接口工作。

```python
class Buffer:
    def __init__(self):
        self.lines = []

    def write(self, text):
        self.lines.append(text)


class PrefixSink:
    def __init__(self, prefix, downstream):
        self._prefix = prefix
        self._downstream = downstream

    def write(self, text):
        self._downstream.write(f"{self._prefix}{text}")


buffer = Buffer()
output = PrefixSink("上午 · ", buffer)
output.write("测量完成")
print(buffer.lines)
```

新增的前缀功能可以与任意满足输出约定的对象组合。测试时使用缓冲区就能看到完整文字。以后更换显示方式，只需要提供另一个下游对象。

## 10.3 继承、重写与共同的行为约定

### 用继承复用共同的实现

子类可以继承基类的方法，也可以重写部分行为。例如，一个标题的标准格式保持一致，某类标题还需要加编号。

```python
class Heading:
    def __init__(self, title):
        self.title = title

    def render(self):
        return self.title


class NumberedHeading(Heading):
    def __init__(self, title, number):
        super().__init__(title)
        self.number = number

    def render(self):
        return f"{self.number}. {super().render()}"


for heading in [Heading("目录"), NumberedHeading("观察结果", 2)]:
    print(heading.render())
```

`super()` 在这个例子中把调用交给基类的相应实现。使用标题的代码可以继续依赖 `render()` 交出字符串。设计继承时，检查子类是否仍遵守调用者依赖的约定。如果一个能力经常独立改变，可将该能力作为成员传入，通过组合选择所需对象。[Python 官方教程的继承](https://docs.python.org/3.12/tutorial/classes.html#inheritance)

### 看哪一种变化需要复用

| 需要解决的问题 | 可选方式 | 核对重点 |
| --- | --- | --- |
| 将输出、存储等能力交给另一个对象 | 组合 | 调用时需要的方法、结果与失败行为 |
| 让不同实现都能参加一项协作 | 协议 | 方法形状和共同的行为约定 |
| 几种对象具有同一基本职责，共享初始化或方法 | 继承 | 重写后仍遵守调用者使用的接口 |
| 给多个函数统一增加外围工作 | 装饰器 | 调用参数、返回值和异常能继续传递 |

如果一个编号标题仍然交出可显示的标题文字，就可以放在使用普通标题的地方。设计子类时，可以挑选几项基类调用者依赖的行为，用同一组用例检查子类。如果变化独立于原有角色，例如是否给文字加前缀，可以让负责转发的组件承担它。

## 10.4 用装饰器复用函数外围的行为

装饰器接收一个函数并交出替代对象。写在定义上方的 `@report_call`，相当于函数定义后用 `report_call` 处理它，再把结果绑定回原函数名。记录日志、统计耗时等重复工作可放进包装函数。

```python
from functools import wraps


def report_call(function):
    @wraps(function)
    def wrapped(*args, **kwargs):
        result = function(*args, **kwargs)
        print(function.__name__, "计算完成")
        return result

    return wrapped


@report_call
def rectangle_area(width, height):
    return width * height


print(rectangle_area(3, height=4))
print(rectangle_area.__name__)
```

`*args` 和 `**kwargs` 接收并转交位置实参与关键字实参。包装函数照常交出计算结果，调用异常也会继续传播。`wraps` 保留原函数名、文档字符串等元数据，帮助调用者和工具识别被包装的函数。[Python 官方文档的 functools.wraps](https://docs.python.org/3.12/library/functools.html#functools.wraps)

### 装饰发生在定义时，包装发生在调用时

执行函数定义时，Python 会用装饰器处理函数对象。以后调用该名字时，执行的是包装后的函数。需要给包装行为提供额外参数时，可以先创建装饰器，再用它接收函数。

```python
from functools import wraps


def report_as(label):
    def decorate(function):
        @wraps(function)
        def wrapped(*args, **kwargs):
            result = function(*args, **kwargs)
            print(label, result)
            return result

        return wrapped

    return decorate


@report_as("换算后的厘米数")
def to_centimeters(meters):
    return meters * 100


print("用于后续计算", to_centimeters(1.25) + 25)
```

`report_as("换算后的厘米数")` 在定义时取得一个带标签的装饰器。包装函数在调用时计算结果并记录。调用处仍能取得数值并继续相加。如果原函数报告错误，包装函数中位于调用之后的记录不会执行。可以另外在明确知道如何处理时记录失败或重新抛出异常。

## 10.5 用迭代协议和泛型复用遍历能力

第 3 章已经通过 `iter` 和 `next` 观察过迭代。自定义对象可以通过 `__iter__` 交出迭代器，使 `for` 和 `list()` 等通用操作能够使用它。迭代器通过 `__next__` 取得下一项，耗尽时抛出 `StopIteration`。

```python
from collections.abc import Iterable
from typing import TypeVar


T = TypeVar("T")


def first(values: Iterable[T]) -> T | None:
    return next(iter(values), None)


class Readings:
    def __init__(self, values):
        self._values = tuple(values)

    def __iter__(self):
        return iter(self._values)


print(first(["东站", "西站"]))
print(first(Readings([18, 20])))
print(list(Readings([18, 20])))
print(first([]))
```

`Readings` 把实际迭代交给元组的迭代器。`T` 表示由调用决定的元素类型，使接口能表达“第一项的类型来自输入元素”。传入字符串列表时，结果标注对应 `str | None`。这种把类型关系写成参数的方式称为泛型。[Python 官方文档的迭代器类型](https://docs.python.org/3.12/library/stdtypes.html#iterator-types) [Python 官方文档的泛型](https://docs.python.org/3.12/library/typing.html#generics)

### 迭代对象和迭代器可以分工

一个可迭代对象可以为每次遍历交出新的迭代器。迭代器自己记住当前的位置，`iter(iterator)` 返回它自身。下面显式实现读取位置和结束条件，再对同一批数据取得两个迭代器。

```python
class ReadingCursor:
    def __init__(self, values):
        self._values = values
        self._position = 0

    def __iter__(self):
        return self

    def __next__(self):
        if self._position >= len(self._values):
            raise StopIteration
        value = self._values[self._position]
        self._position += 1
        return value


class Series:
    def __init__(self, values):
        self._values = tuple(values)

    def __iter__(self):
        return ReadingCursor(self._values)


series = Series([18, 20, 22])
first = iter(series)
second = iter(series)
print("两个游标各取第一项", next(first), next(second))
print("第一个剩下", list(first))
print("第一个耗尽", list(first))
print("再次遍历序列", list(series))
```

两个游标的第一项都是 18。读完第一个游标后，它仍停在末尾。再次遍历 `series` 时会创建新游标，因此又能取得完整数据。若底层已有合适的迭代器，像前例一样直接返回 `iter(self._values)` 可以复用这些操作。

### 泛型把不同位置的类型关系写出来

`Iterable[T]` 表示可逐项取得 `T` 类型的值。使用同一个 `T` 可以让函数的返回值和输入建立联系。类也可以用类型变量描述自己保存和交出的值。

```python
from typing import Generic, TypeVar


T = TypeVar("T")

class Box(Generic[T]):
    def __init__(self, value: T):
        self._value = value

    def get(self) -> T:
        return self._value


count = Box(18)
title = Box("东站")
print("可用于计算", count.get() + 2)
print("可用于拼接", title.get() + "读数")
```

类型检查工具可以从构造实参推导出 `count` 保存整数、`title` 保存字符串。这样两处 `get()` 具有相应的结果类型。泛型帮助描述关系，运行时仍由构造方法和调用者遵守数据约定。

## 10.6 用异步协作等待多个结果

`async def` 定义异步函数。调用它会得到协程对象，通过 `await` 可以等待它完成。协程等待可以让出执行权的操作时，事件循环能够推进其他任务。适合一起等待的独立操作可以用 `asyncio.gather` 组织。

| 表达方式 | 执行含义 |
| --- | --- |
| 调用异步函数 | 创建协程对象，准备工作 |
| `await operation()` | 等待该协程完成后继续本层步骤 |
| 逐个写 `await` | 前一项完成后才开始等待下一项 |
| `await asyncio.gather(a(), b())` | 让事件循环推进多个可并发等待的协程 |

若后一项依赖前一项的结果，逐项等待能表达这个依赖。若两个结果来自互相独立的来源，可以一起等待。下面观察各自完成的时刻，再观察汇总的结果顺序。

```python
import asyncio
import sys


async def read_station(name, delay, value):
    await asyncio.sleep(delay)
    print(name, "完成")
    return name, value


async def main():
    results = await asyncio.gather(
        read_station("东站", 0.03, 18),
        read_station("西站", 0.01, 20),
    )
    print("汇总", results)


if sys.platform == "emscripten":
    __lesson_task__ = asyncio.ensure_future(main())
else:
    asyncio.run(main())
```

示例用 `sleep` 模拟等待，西站可以先完成。`gather` 按传入协程的顺序交出汇总结果，因此汇总中东站仍排在前面。实际访问外部服务时，需要给每项等待规定超时和失败处理。网页运行器已有事件循环，示例最后几行用它启动协程。[Python 官方文档的协程与任务](https://docs.python.org/3.12/library/asyncio-task.html#asyncio.gather)

### 为每个结果保留超时状态

多个等待任务中，有的可能按时完成，有的可能超时。可以把超时处理放到单项任务内部，让它交出明确的状态，再将各项结果汇总。这里用 `asyncio.wait_for()` 为每个模拟读取设置等待期限。

```python
import asyncio
import sys


async def read_after(delay, value):
    await asyncio.sleep(delay)
    return value


async def read_with_deadline(name, delay, value):
    try:
        reading = await asyncio.wait_for(read_after(delay, value), timeout=0.1)
    except asyncio.TimeoutError:
        return name, "超时", None
    return name, "完成", reading


async def main():
    results = await asyncio.gather(
        read_with_deadline("东站", 0, 18),
        read_with_deadline("西站", 1, 20),
    )
    for name, status, reading in results:
        print(name, status, reading)


if sys.platform == "emscripten":
    __lesson_task__ = asyncio.ensure_future(main())
else:
    asyncio.run(main())
```

西站的等待超时后被取消，东站的读数仍可使用。这里仅处理了预期的超时。其他异常仍会沿调用链报告。异步等待适合同时推进多个外部等待，本章的报名更新则依赖已有名单和保存的结果，必须按原有顺序完成。[Python 官方文档的超时处理](https://docs.python.org/3.12/library/asyncio-task.html#asyncio.wait_for)

## 10.7 回到案例 为报名回执更换通知方式

第 9 章的 `submit` 在报名保存成功后返回回执。新增的 `submit_and_notify` 先取得这一回执，再交给提供 `send(message)` 的通知对象。存储异常会沿调用链传播。通知对象报告已知的发送故障时，调用者会同时取得报名回执和“通知待处理”。

| 要替换的对象或能力 | 负责的工作 | 核对方式 |
| --- | --- | --- |
| 第 9 章的报名能力 | 检查规则，必要时完成保存，再交出回执 | 用同一批请求核对回执和名单 |
| 终端通知 | 把回执写到输出 | 查看五条回执 |
| 内存通知 | 按次序保留收到的文字 | 比较消息列表 |
| 模拟故障的通知 | 报告预期的发送异常 | 核对报名已经保存，通知待处理 |
| 模拟故障的存储 | 报告保存异常 | 核对没有生成通知，保存状态未更新 |

协调函数用 `Callable[[str], str]` 说明它需要一个接收学号并交出回执的可调用对象。这里用 `partial(submit, store)` 固定原来函数的存储参数。网页示例加载第 9 章同一份项目代码，报名规则和文件格式由那个项目定义。

### 交付带活动名称的通知

实现 `PrefixNotifier.send()`，给每条回执加上活动名称，再交给已有的通知对象。先写出 `S01：通过` 应如何显示，再运行。遇到发送异常时，协调函数还要能给出「通知待处理」，并保留已登记的学号。

| 验收情形 | 预期结果 |
| --- | --- |
| 同一批五条请求 | 回执和名单与第 9 章相同，每条通知都带活动名称 |
| 通知对象报告发送故障 | 报名通过，通知待处理，名单仍有 S01 |
| 存储对象报告保存故障 | 失败交给调用者，名单为空，通知列表为空 |

```python notifier-task campus
from campus import Activity, MemoryStore, submit


class NoticeError(Exception):
    pass


class RecordingNotifier:
    def __init__(self):
        self.messages = []

    def send(self, message):
        self.messages.append(message)


class PrefixNotifier:
    def __init__(self, title, target):
        self.title = title
        self.target = target

    def send(self, message):
        # 加上活动名称和空格，再转交通知。
        raise NotImplementedError("请先完成 PrefixNotifier.send()")


def submit_and_notify(store, raw_id, notifier):
    receipt = submit(store, raw_id)
    student = raw_id.strip() or "（空白）"
    try:
        notifier.send(f"{student}：{receipt}")
    except NoticeError:
        return receipt, "通知待处理"
    return receipt, "已通知"


requests = ["S01", " ", "S02", "S03", "S01"]
receipts = ["通过", "空学号", "通过", "满员", "重复"]
store = MemoryStore(Activity("博物馆", 2))
recording = RecordingNotifier()
notifier = PrefixNotifier("博物馆", recording)
outcomes = [submit_and_notify(store, raw, notifier) for raw in requests]
assert outcomes == [(receipt, "已通知") for receipt in receipts]
assert store.load().students == ("S01", "S02")
assert recording.messages == [
    "博物馆 S01：通过", "博物馆 （空白）：空学号", "博物馆 S02：通过",
    "博物馆 S03：满员", "博物馆 S01：重复",
]
print("带活动名的通知", recording.messages)


class FailingNotifier:
    def send(self, message):
        raise NoticeError("通知暂时不可用")


store = MemoryStore(Activity("博物馆", 2))
notifier = PrefixNotifier("博物馆", FailingNotifier())
assert submit_and_notify(store, "S01", notifier) == ("通过", "通知待处理")
assert store.load().students == ("S01",)
print("通知故障时保留已保存名单")


class ReadOnlyStore(MemoryStore):
    def save(self, activity):
        raise OSError("存储不可写")


store = ReadOnlyStore(Activity("博物馆", 2))
recording = RecordingNotifier()
try:
    submit_and_notify(store, "S01", PrefixNotifier("博物馆", recording))
except OSError:
    assert store.load().students == ()
    assert recording.messages == []
else:
    raise AssertionError("应报告保存失败")
print("保存故障时未发送通知")
print("通知扩展验收通过")
```

### 对照协议和完整实现

```python notifier-reference campus solution
from campus import Activity, MemoryStore, submit
from collections.abc import Callable
from functools import partial
from typing import Protocol


class NoticeError(Exception):
    pass


class Notifier(Protocol):
    def send(self, message: str) -> None:
        ...


class ConsoleNotifier:
    def send(self, message: str) -> None:
        print(message)


class RecordingNotifier:
    def __init__(self):
        self.messages: list[str] = []

    def send(self, message: str) -> None:
        self.messages.append(message)


class PrefixNotifier:
    def __init__(self, title: str, target: Notifier):
        self.title = title
        self.target = target

    def send(self, message: str) -> None:
        self.target.send(f"{self.title} {message}")


class FailingNotifier:
    def send(self, message: str) -> None:
        raise NoticeError("通知暂时不可用")


def submit_and_notify(
    submit_request: Callable[[str], str], raw_id: str, notifier: Notifier
) -> tuple[str, str]:
    status = submit_request(raw_id)
    student_id = raw_id.strip() or "（空白）"
    try:
        notifier.send(f"{student_id}：{status}")
    except NoticeError:
        return status, "通知待处理"
    return status, "已通知"
```

### 沿完成状态决定下一步

终端和内存两种通知收到相同顺序的回执。内存通知额外记录活动名称，两次的最终名单都为 `("S01", "S02")`。模拟通知故障时，名单中已包含 S01，可以按原回执补发。模拟保存故障时，应先处理存储错误。

| 观察到的情况 | 已完成的状态 | 之后可以做什么 |
| --- | --- | --- |
| 报名通过，已通知 | 报名已保存，通知完成 | 正常查阅回执 |
| 报名通过，通知待处理 | 报名已保存 | 以原回执补发 |
| 保存失败 | 未提交新的报名状态 | 存储恢复后再提交报名 |

把原有用例保留到扩展之后，能检查代码是否仍按约定给出回执和状态。如果以后要引入多个可并发的通知渠道，可以在取得同一条回执之后组织它们，各自记录结果。这样每项通知的失败都有对应的处理位置。
