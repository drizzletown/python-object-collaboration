# 导论 从解决问题到程序设计
> 从一次博物馆参观出发，学习怎样分配对象职责、组织协作，以及如何在一项能力尚未实现时继续设计程序。

## 1 对象协作编程模型

### 从现实任务划定程序的范围

班级计划组织 30 名同学参观博物馆。活动组织者收集报名、确认车辆和预约、发布集合通知。每项工作都依赖别人的信息或行动。联系车辆之前要知道预计人数，发出通知之前要核实时间和地点。分析问题时，先弄清希望得到什么结果，以及哪些人、事物和信息参与其中。

本教材选择其中一段工作构造程序。学生提交学号，程序依据名额和名单判断能否报名，更新记录并生成回执。车辆调度和场馆预约仍由活动组织者负责。这个范围决定了程序需要保存哪些信息、处理哪些请求。

先看最小的一步。容量和已报名人数都是整数，二者相减得到剩余名额。把 `registered` 从 29 改成 30，再运行代码观察判断结果。

```python
capacity = 30
registered = 29
remaining = capacity - registered
print(f"剩余名额：{remaining}")
print("还有空位：", remaining > 0)
```

### 为每个对象分配职责

一个人数只能回答“还剩几个名额”。要识别同一学号是否重复提交，还需要保存报名名单，并明确谁来检查和修改它。我们可以从下面几种职责入手。

- 报名请求带来活动编号和学生学号。处理前清理学号首尾空白，拒绝空学号。
- 活动保存容量和已登记的学号，负责判定重复与满员。登记成功时更新名单。
- 报名流程协调读取、登记和保存。它把请求交给活动，保存成功后再返回通过回执。
- 存储负责读写记录，回执展示负责将结果呈现给学生。

先确定每项规则由谁维护，再安排对象之间怎样传递数据、调用能力并处理返回结果，这就是本书采用的对象协作编程模型。名单可以由列表或字典表示，人数可以是整数，活动可以由自定义类表示。是否定义一个类，要看相关状态和规则是否适合由同一个对象管理。

从活动自身看，问题是“怎样检查并登记这个学号”。书中把它称为第一视角，适合用对象的方法表达。从外部流程看，问题是“谁读出活动、调用登记并保存结果”。书中把它称为第三视角，适合用函数描述这些步骤。两种视角分别说明活动提供什么能力，以及流程怎样使用它。

## 2 假设三部曲

### 把缺少的能力写成可检验的约定

报名流程要读取已有名单，也要把成功报名保存下来。文件格式、读取失败的处理方式和写入步骤还未确定时，可以先约定存储要提供的能力，用这份约定推进其余设计。

- 建立假设。约定 `load()` 返回一份独立的名单副本。约定 `save(updated)` 在成功时保存新名单，失败时报告错误。写清输入、结果以及失败时的行为，调用方才知道能依赖什么。
- 使用假设。主流程先排除空学号，再读取名单并检查重复和满员。只有通过检查才保存，且保存成功后才发出“通过”回执。先用内存替身验证这个顺序。
- 兑现假设。实现文件读写，验证保存后重新读取能拿到最新名单，损坏的文件会报告错误。如果实现无法满足原约定，修改约定后也要检查依赖它的流程。

下面的示例把两个内存函数交给报名流程。观察 `submit` 怎样使用它们。再把最后一次调用的学号换成 S03，比较“重复”和“满员”时的名单。

```python
def submit(student_id, capacity, load, save):
    student_id = student_id.strip()
    if not student_id:
        return "空学号"

    roster = load()
    if student_id in roster:
        return "重复"
    if len(roster) >= capacity:
        return "满员"

    roster.append(student_id)
    save(roster)
    return "通过"


stored = ["S01"]

def load_from_memory():
    return stored.copy()


def save_to_memory(roster):
    stored[:] = roster


print(submit("S02", 2, load_from_memory, save_to_memory))
print(submit("S02", 2, load_from_memory, save_to_memory))
print(stored)
```

第一次提交保存 S02，第二次提交返回“重复”。`load_from_memory` 特意返回副本。如果直接返回 `stored`，`roster.append` 就会在调用保存函数之前改动原名单。可以试着让保存函数一开始就抛出 `OSError`，在浏览器的运行结果里观察流程停在何处。内存示例验证了调用顺序，文件写入和跨次读取留到综合项目验证。

### 兑现假设时继续分解

实现 `load()` 时，会发现另一个问题。文件里的 JSON 即使能够解析，名单仍可能含有重复学号，人数也可能超过容量。于是再建立一层约定，先假设有个校验函数能把解析结果变成符合规则的活动对象，在读取流程中调用它，再实现并测试校验规则。

子任务有了可直接实现和验证的办法，就可以动手完成。校验通过测试以后，回到文件读取，再回到完整报名流程，逐层检查前面的约定是否成立。这里的“递归”指同一套设计方法可以用在更小的子问题上。程序运行时是否需要函数递归，由具体任务决定。

## 3 从对象协作需求推导 Python 语言功能

学习一种功能之前，先指出当前方案缺少哪种表达能力。报名案例中的每次扩展都给出了一个选择语言功能的理由。

### 表示信息并组织处理

- 要表示活动名称、容量和“还有空位”的判断，使用字符串、整数和布尔值。给数据绑定名字，用表达式从已有信息算出新结果。
- 要保存学号并按提交顺序处理请求，可以用列表保存序列，用集合判断成员是否已经存在，用字典按活动编号查找记录。根据需要进行的操作选容器。
- 要让程序在空学号、重复、满员和通过之间作出不同处理，用条件语句表达分支优先级。要处理一批请求，用循环逐个应用规则。

### 为协作建立清楚的边界

- 要在单次报名和批量处理中使用同一规则，用函数约定接收什么、返回什么，以及何时改变名单。调用方可以单独验证函数的行为。
- 要让不同活动各有容量和名单，并由活动自身维护报名规则，用类定义活动对象，把相关状态和方法放在一起。多个活动、报名服务和存储再通过组合形成完整流程。
- 要在报名流程之外安排文件读写、记录失败和验证结果，用模块组织代码，用异常传递无法完成的操作，用测试检查返回结果和状态变化。用文件接口和 JSON 将活动信息保留到下一次运行。
- 要把终端通知换成另一种通知方式，用协议描述双方都能满足的调用约定。流程继续按这个约定发送消息，新的通知对象负责具体的交付方式。

判断选择是否合适，可以追问两件事。修改某条规则时需要改动几处？能否单独验证承担这条规则的对象或函数？例如，增加候补策略时，应先定义活动在满员后怎样更新状态，再检查流程是否需要保存候补记录。
