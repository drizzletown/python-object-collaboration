# 附录 B 项目工具链与开发实践
> 在教材示例中练习复现问题、验证修改、组织程序和记录变化，理解常见开发工具各自负责什么。

## B.1 让一次运行可以被重新核对

完成一个程序时，记录使用了哪些输入、预计得到什么、实际发生了什么。比如“重复报名不应改变名单”，需要写明开始时名单里有谁、提交哪个学号、预期回执和预期名单。这样过一段时间，另一位读者也可以用相同的条件核对。

| 应记录的内容 | 可以怎样写 |
| --- | --- |
| 输入和初始状态 | 容量 1，已有 S01，再提交 S01 |
| 预期回执 | 重复 |
| 预期状态 | 仍只有 S01 |
| 执行观察 | 实际回执为满员，名单仍只有 S01 |
| 定位过程 | 检查重复与容量判断的先后 |

这样的记录可以直接转成测试。若只有“程序报错”或“结果有问题”，要先补上产生问题的最小输入。

## B.2 把计算结果和显示方式分开验证

可以先让小函数交出可比较的对象，再由调用处输出。把预期写成表格或几条断言，便于在改变显示方式或替换数据来源后复查。

```python
def normalize_names(values):
    names = []
    for raw in values:
        text = raw.strip()
        if text:
            names.append(text)
    return names


cases = [
    ([], []),
    ([" 甲 ", " ", "乙"], ["甲", "乙"]),
    (["甲", "甲"], ["甲", "甲"]),
]
for values, expected in cases:
    result = normalize_names(values)
    print("输入与结果", values, result)
    assert result == expected

print("三个用例通过")
```

最后一组检查重复项是否保留。如果任务改为去重，应先明确先后顺序和预期输出，再修改实现与相应测试。如果任务只要求调整显示，则可以保留这三组原有用例，另外核对显示结果。

## B.3 用工具解决不同的开发问题

| 工具或机制 | 能检查什么 | 仍需要怎样验证 |
| --- | --- | --- |
| 格式化工具 | 缩进、换行与布局 | 确认原有结果仍正确 |
| 静态检查 | 部分名字、导入和类型问题 | 运行实际场景检查业务规则 |
| 调试器 | 暂停执行，观察调用、对象与局部变量 | 找到最早出现错误结果的步骤 |
| 自动测试 | 重复核对明确的预期 | 根据任务增补缺失用例 |
| 日志 | 记录运行时发生的事件 | 用最小输入重现，再确认原因 |
| 版本记录 | 追踪每次修改了什么及其目的 | 复查差异和相关用例 |

这些工具可以配合使用。例如类型检查能提示函数可能收到 `None`，测试则能检查收到 `None` 时的具体行为。单步调试可以确认问题出在检查前还是状态写入后，日志可以帮助收集以后需要重现的输入条件。

## B.4 认识程序依赖与模块边界

Python 解释器自带标准库。第 9 章用其中的 `json`、`pathlib` 和 `tempfile` 等能力完成文件存储。项目若使用第三方库，则要另外知道它提供什么能力、使用的版本，以及哪些场景需要复查。读到导入语句时，可以先沿着名字确认它来自语言内置能力、标准库、项目模块还是第三方库。

一个项目可以把规则、外部资源和入口放在不同模块。阅读时先找入口，然后沿调用看它如何取得数据、请哪个对象处理、将结果交给谁。测试时则可以直接使用负责规则的对象，也可以从入口运行完整流程。[第 6 章 多对象协作与程序组织](06.md)

## B.5 每次修改都留下可以说明的结果

准备修改时，先写出变更的需求。修改完成后，比较发生变化的内容，并运行直接相关的用例。以容量判断为例，从“已登记人数大于容量时拒绝”改成“已登记人数达到容量时拒绝”，就要用“恰好满员”来区分两个版本。

版本记录可以把一次修改及其原因保留下来。描述一次变化时，可以写“满员时拒绝新学号，保留重复判断优先级”，再附上恰好满员和满员后重复的核对结果。将范围明确的改变和用例放在一起，之后继续扩展时就知道哪些行为已经经过验证。

扩展功能前，可以把最重要的原有场景保存为一组检查。第 10 章更换通知方式时，就会重用第 9 章的五条请求，并增加存储失败和通知失败的情形。[第 10 章 对象协作系统的复用与演化](10.md)
