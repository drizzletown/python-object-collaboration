0.1 一次班级参观活动

班级准备组织 30 名同学参观博物馆。大家要在预约时段到馆，参观结束后一起返程。

参与任务的对象集合

这件事需要同学、组织者、博物馆，也需要运输方、车辆和驾驶员。同学确认是否参加，博物馆提供参观时段，运输方和驾驶员负责接送。把完成这项任务所需的对象放在一起，就得到这次参观的对象集合。

组织参观的协作过程

组织者向同学确认人数，与博物馆约定参观时段，再用人数和时段请运输方安排接送。车辆和时间确认后，组织者通知同学集合，驾驶员按约定接送，博物馆按预约接待。前一步确认的信息成为后一步行动的依据，各方就能把参观活动办成。

用同一个视角看日常任务

要办成的事对象集合对象协作过程
小组汇报负责查资料、整理材料和汇报的同学查到的资料交给负责整理的同学，整理成提纲后由汇报人讲解
订一份外卖顾客、餐馆、配送员顾客下单，餐馆按订单备餐，配送员取餐后交给顾客
到图书馆借书读者、图书、图书管理员读者选书后交给管理员，管理员登记借阅并告知归还日期

从求解问题的角度看，可以先根据目标找到合适的对象，再安排它们沟通协作，发挥各自的能力。找到的对象构成对象集合，它们交换信息、接手工作并交出结果的方式构成对象协作过程。

求解方案 = 对象集合 + 对象协作过程

0.2 对象协作编程模型

要把求解方案写成计算机能执行的程序，就要描述对象集合和对象协作过程。以办理报名为例，程序需要描述活动、报名名单和一条带学号的请求。活动有容量，名单保存已确认参加的同学，出发前还可以用它点名。

程序还要描述对象怎样配合。收到请求后，先用学号查名单，再检查活动名额。符合条件时更新名单，最后交回报名结果。本书把这种写法称为对象协作编程模型。

程序 = 描述对象 + 描述对象协作过程

第一视角 从对象自身描述行为

从驾驶员的角度，可以把接送写成一个任务。四个编号步骤都属于这个任务。每个步骤的具体工作再缩进一级，异常反馈则属于执行接送时的条件分支。

任务：按约定完成乘客接送
    1. 输入
        1.1 接收集合地点、目的地、接送时间和乘客名单。
    2. 处理：准备接送
        2.1 检查车辆，确认行驶路线。
    3. 处理：执行接送
        3.1 按约定的时间和路线接送乘客。
        3.2 如果途中出现异常：
            3.2.1 及时向组织者反馈情况。
    4. 输出结果
        4.1 向组织者报告接送是否完成。

这种从对象本身出发的描述叫第一视角。它关注对象收到哪些信息、怎样完成职责、交出什么结果。

第三视角 从外部组织协作

从整个活动的角度，可以这样安排驾驶员、参加者和博物馆之间的配合。

任务：组织班级参观博物馆
    1. 输入
        1.1 收集同学的报名信息，取得场馆可预约时段。
    2. 处理：确认车辆和参观时段
        2.1 汇总报名名单，按人数向运输方查询座位。
        2.2 如果座位不足，调整用车安排，再核对座位。
        2.3 确认接送时间后，向博物馆确认预约。
    3. 处理：通知并执行行程
        3.1 向参加者通知集合时间和地点。
        3.2 出发前按名单点名，请驾驶员按约定接送。
        3.3 完成参观后再次点名，组织返程。
    4. 输出结果
        4.1 向班级报告参观和返程的完成情况。

这种从外部使用对象能力、安排多个对象共同完成任务的描述叫第三视角。组织者需要知道驾驶员能否按时接送，以及如何取得确认。驾驶员则需要知道怎样完成接送。两种视角共同说明一项工作怎样办成。

两种视角怎样对接

当组织者发出接送请求，整体安排只需说明交给驾驶员哪些信息、何时能得到确认。驾驶员负责检查车况、选择路线、报告完成情况。这两部分以同一项约定衔接。以后更换驾驶员，只要仍按同一约定提供接送和反馈，原来的活动安排就可以继续使用。

对象自身可以负责检查与自己有关的条件。例如，车辆的座位数由运输方确认。涉及多项条件的取舍则由组织者完成，例如比较预约时段、可用车辆和参加者的集合时间。看到一项工作时，可以先问它只涉及一个角色的职责，还是需要把几个角色的结果接起来。

0.3 假设三部曲

遇到一项暂时缺少的能力，只要眼下还用不到真实结果，就可以先大胆假设它可用。说清它会交回什么，再把预期结果交给后续步骤，先完成整体方案。等到需要真实结果时，再兑现假设。

先排出参观日程

班级已经约好参观时段，车辆还没订好。组织者可以先用暂定的接送时间排日程，其他准备工作也就可以开始了。

任务：拟定班级参观日程
    1. 输入：报名人数、场馆预约时段和用车要求。
    2. 处理：先拟定日程
        2.1 建立假设：能取得符合要求的接送服务，
            并得到发车、到馆和返程时间。
        2.2 使用假设：用暂定的发车时间安排集合，
            再把到馆和返程时间与预约时段衔接，排出参观日程。
    3. 处理：发正式通知前兑现假设
        3.1 与运输方确认车辆和实际接送时间。
        3.2 按确认的时间核对日程，必要时调整。
    4. 输出结果：已确认的参观日程和接送安排。

程序设计中的兑现也有几种做法。可以自己实现所需能力，请别人按约定实现，或使用语言及现有程序库提供的功能。无论用哪种做法，都要检查实际结果是否符合约定。

什么时候应当兑现

“能得到合适的接送安排”是一个起点。把它写成可以检验的假设，还需要说明要提供什么条件、会交回什么信息。在这个例子里，提供报名人数和预约时段，得到暂定的发车、到馆和返程时间。用这些具体结果就能继续排出集合与参观日程。

日程草案允许暂定时间。准备发正式通知时，参加者将按通知行动，这时应拿到实际接送安排。如果运输方给出的到馆时间晚于预约时间，组织者就要重排日程，再决定是否能发布通知。程序也可以先用可预期的数据检查主流程，在结果需要保存或对外使用前验证真实的实现。

兑现遇到新困难时再用一次三部曲

在步骤 3.1 确认用车时，如果一辆车坐不下全班、需要分乘两辆车，组织者就多了一项工作。可以把乘车分组作为子任务，用同样的方法处理。

子任务：确定乘车分组（步骤 3.1）
    3.1.1 建立假设：能按车辆座位数，为两辆车各取得一份乘车名单。
    3.1.2 使用假设：用两份暂定名单，分别拟定各车的接送安排。
    3.1.3 兑现假设：分配乘客并核对座位，把确认的分组交回用车任务。

分组落实后，组织者就能继续确认接送安排，再用确认的时间核对参观日程。把同一套方法用到子任务上，就是递归使用假设三部曲。

0.4 用两条线索理解程序构造

对象协作模型帮助我们确定需要哪些对象、它们各自做什么，以及工作怎样衔接。假设三部曲帮助我们在某项能力暂时缺少时继续设计，并在适当的时候补上它。

在报名系统里，可以先约定能读到活动容量和报名名单，用这两项信息设计名额检查与登记流程。等到要处理真实记录时，可以借助 Python 标准库读取文件，再按约定交回数据。第 9 章会演示这个过程。

递归使用假设三部曲发生在设计过程中。递归函数则是运行中的函数再次调用自身。报名系统可以用前一种方式设计，再用普通调用和循环实现。

还可以用一条具体情形检查设计。例如，名单只剩一个名额，两条请求先后到达。第一条结果应当更新名单，第二条则要依据更新后的名单判断。能说出每一步取得什么、修改什么、交出什么，就可以进一步选用合适的语言机制。

0.5 从描述需要出发认识 Python 的语言功能

描述对象 从一个数据到一种角色

最先遇到的需要是表达信息。参加人数、票价、活动名称和报名是否成功具有不同含义。Python 提供整数、浮点数、布尔值和字符串来表示这些信息，也提供一种专门的值表示某项信息缺失。给对象绑定名字，便于在后续步骤中引用它。

记录多起来，就要把对象组织起来。列表适合按顺序保存名单，元组可以把固定的一组值放在一起，字典可以按学号查找成绩，集合便于判断成员和去重。选择哪种容器，取决于信息之间的关系和需要进行的操作。

活动、课程或订单有自己的状态和职责。Python 可以用类定义这类对象，用属性保存信息，用方法描述对象自身的行为。更大的结构由多个对象组合而成，例如订单包含多个商品条目。几个名字也可以指向同一个对象。理解这一点，有助于判断一处修改会怎样影响使用同一对象的其他地方。

描述协作 从一次操作到完整流程

最简单的协作是取得信息、进行计算、请求某项工作，再使用它的结果。Python 用表达式和运算符描述计算，用属性访问和方法调用使用对象的信息与行为。普通函数可以从外部处理信息或组织多个对象协作。

任务遇到不同情形，就需要条件判断。比如报名已满时应拒绝新申请。任务要对一批对象重复处理，就需要循环和迭代。比如逐个核对名单。资格检查、费用结算和通知生成等工作会在多处用到，可以把它们写成独立的函数，约定接收什么、交回什么。

组织、检验并扩展协作

对象和函数逐渐增多时，可以用模块和包组织相关能力，用接口约定说明各部分怎样配合。输入有误、文件打不开或外部服务暂时不可用时，可以用异常处理规定失败时的行为，再借助测试、调试和日志检验结果。文件读写、资源管理和数据交换格式则让程序能够与外部环境交换信息。

需要更换通知方式或增加活动类型时，可以用组合、继承、多态或协议复用和替换能力。需要同时等待多个外部操作时，还可以学习异步协作。各章会在出现相应需求后逐步引入这些工具。下面的章节安排把这些需求、语言机制和学习任务对应起来。

从任务推导需要使用的工具

求解时的问题需要表达的内容教材中学习的能力
数据有哪些，彼此是什么关系单个量、顺序、按编号查找、成员关系基础对象、名字、容器
一条请求该怎么处理先做什么，满足条件后做什么，何时结束表达式、条件、循环

这些问题可以反复出现。一个处理文本的短程序可能只要基础对象和函数。一个要保存名单、重新打开并发送通知的系统，还需要明确状态、资源和失败发生在哪里。任务的变化决定要增加哪些工具。

0.6 怎样沿着这条线索学习

每章先提出一项实际任务，尝试用已有知识处理，找出还缺少的描述能力，再学习相应的 Python 功能，最后实现并检验结果。已有条件足以解决时，可以直接做。遇到暂时无法实现的能力，从第 1 章起就可以用假设三部曲推进。

校园活动报名是全书的贯穿案例。成绩统计、文本处理和费用结算等短案例帮助读者把同一种方法用到其他问题。阅读时，可以先用自然语言说出有哪些对象、各自负责什么、怎样传递信息，再看 Python 如何表达这些步骤。

沿同一份任务练到独立交付

学习阶段动手完成的事怎样确认自己学会了
第 1–2 章改一行报名人数，再试着选择和修改容器能先预测输出，并解释改动影响了哪份数据
第 3–4 章跟踪一批请求，再把资格判断写成函数回执顺序与最终名单都符合预期
第 5–6 章让活动各自维护名单，再接好目录和报名服务同一个学号可在两场活动分别登记，查询失败时有明确回执
第 7–8 章让测试先暴露问题，再修复判断或保存流程除了回执，还能核对失败前后的名单或文件
第 9–10 章自己实现余量查询和一种通知方式按验收条件检查新功能、原报名规则与失败后的状态

用一组结果检验自己的理解

先读案例里的任务和预期结果。中段讲到一个机制时，可以在独立例子里先预测输出，再在网页上运行。试着每次只改一个输入，观察是对象、状态、还是执行路径发生了变化。最后回到案例，解释为什么选用了这些对象和操作。

例如，学习“名额检查”时，可以分别想象只剩一个名额、没有名额和同一人再次报名。先写出预期回执和名单，再与示例结果核对。以后遇到借阅或预约任务，也可以照这个方式列出几种情形，看看已有的解法哪些能够直接使用。

全书章节结构与教学安排

前两章表示和组织数据，第 3、4 章安排流程并封装处理能力，第 5、6 章构造对象并组织系统，第 7、8 章检验协作并使用外部资源，第 9、10 章完成和扩展一个综合项目。

从数据到独立处理能力

  • 第 1 章 基础数据对象与信息处理。认识基础对象、名字绑定、运算和信息输出。用活动名称、人数和票价计算费用与剩余名额，生成一条报名提示。
  • 第 2 章 容器对象与数据组织。比较列表、元组、字典和集合的用途，理解引用、可变性与复制。为报名名单和活动配置选用合适的容器，验证修改时会影响哪些数据。
  • 第 3 章 对象协作的流程控制。用条件、循环和迭代表示协作步骤。批量处理报名请求，核对重复、满员和正常报名时的结果。
  • 第 4 章 第三视角 函数与协作封装。学习参数、返回值和函数作为对象的用法。把资格检查、单次登记与批量处理组织成可分别调用和检验的能力。

从专属对象到可靠协作

  • 第 5 章 第一视角 自定义对象与类。学习类、实例、属性和方法。构造能维护容量与名单的活动对象，验证不同活动独立管理各自的状态。
  • 第 6 章 多对象协作与程序组织。学习对象组合、接口约定、类型标注和模块组织。划分活动、查询和报名服务的职责，并说明各部分如何交换信息。
  • 第 7 章 对象协作的可靠性。学习输入校验、异常、调试、测试和日志。为正常与失败情形编写检查，验证返回结果和报名状态。
  • 第 8 章 对象与外部环境的协作。学习路径、文件读写、资源管理及常见的数据交换格式。保存和恢复报名数据，并生成可在表格软件中打开的名单。

构造并扩展完整系统

  • 第 9 章 综合项目 递归假设驱动的程序构造。明确目标与验收条件，先用内存中的记录验证主流程，再逐层兑现文件存储和数据检查的假设。交付能够运行和验证的校园活动报名系统。
  • 第 10 章 对象协作系统的复用与演化。学习用组合和协议替换能力，了解装饰器和异步协作。更换报名通知方式，再用测试检查原有报名规则。

按需查阅三个附录。第 1 章开始时可查附录 A 运行环境与学习工具。从函数和模块实践开始，可查附录 B 项目工具链与开发实践。遇到语言机制或标准库用法时，可查附录 C 语言速查与标准库索引。
